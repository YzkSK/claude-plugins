# 保守性レビュー

バグ・安全性は ponytail-review の観点で見る。この skill は、バグではない可読性・保守性の指摘に基準を足す。

## 探すもの

1. **嘘**: 名前・コメント・型と実際の挙動のズレ。副作用が名前に出ていない。
2. **同じ知識の重複**: 一つの仕様変更で複数箇所を直す必要がある。
3. **隠れた依存**: 呼び出し順、グローバル状態、`!` で隠した前提。
4. **解読が要る形**: 前後を追わないと意味が分からない式や分岐。
5. **不要な形**: 使われない引数、到達しない防御コード、一実装だけの抽象。

## 指摘の形

指摘は必ず次の3行で書く。

- **場所**: `file:line`
- **シナリオ**: 次のどちらかを、このコードの具体的な名前を使って一文で書く。
  - 誤読: 「`X` を見た人は A と考えるが、実際は B なので C が起きる」
  - 直し漏れ: 「仕様 `Y` が変わると `P` と `Q` を直す必要があり、`Q` を漏らすと C が起きる」
- **修正**: 最小の変更。可能なら行を減らす案。

この形で書けないものは報告しない。

## 報告前の確認

- 「共通化すべき」という指摘は、二つが同じ仕様変更で必ず一緒に変わるときだけ成り立つ。単位やラベルだけ違う短い関数は、偶然似ているだけなので対象にしない。
- 修正案が元のコードより理解に時間がかかるなら、指摘を取り下げる。
- `shortcut:` コメントで限界が書かれたものは、判断済みとして扱う。

## 出力

シナリオの被害が大きい順に並べる。最後に、残すべき判断があれば一行で書く。指摘がなければ `保守性の指摘なし` と、確認した範囲を一行で書く。
